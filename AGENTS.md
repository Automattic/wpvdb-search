# AGENTS.md

Agent guidance for this repository. Keep this file focused on non-obvious constraints and correctness gotchas. Public usage documentation belongs in `README.md`.

## Boundaries

- Do not add credentials, tokens, application passwords, site-specific hostnames, or private deployment details.
- Keep UI, demo page rendering, public Smart Search REST routing, example prompts, and browser assets in `https://github.com/rbcorrales/wpvdb-smart-search`.
- Do not add ingestion, queueing, provider settings, or embedding storage ownership here. Those belong in `https://github.com/rbcorrales/wpvdb`.
- Keep Playground fixture behavior in `https://github.com/rbcorrales/wpvdb-playground-demo`. This repo can expose hooks and fallbacks, but it should not hardcode demo models or sample data.

## Search correctness

- Every embeddings table read that ranks or compares vectors must scope by the embedding model used for that request. Do not substitute `Settings::get_active_model()` after a query vector has already been generated with another model.
- Mixed model rows can coexist during migrations. Returning rows from different vector spaces produces meaningless rankings, even when the SQL technically succeeds.
- `Search::related_to_post()` compares stored source vectors. It should not re-embed the source post.
- The SQLite related-post fallback stores vectors as JSON text and computes cosine distance in PHP. It is for Playground and small SQLite installations, not a replacement for MariaDB's native vector search at a corpus scale.
- Sparse mode should degrade to an empty result set if the FULLTEXT index is unavailable or the query has no usable terms.

## Public API gotchas

- Keep result projection explicit. Consumers should request fields rather than receiving UI-only payloads by default.
- The semantic search Ability intentionally does not expose arbitrary model selection. Agent callers should not accidentally search across heterogeneous vector spaces.
- `include_debug` can expose operational metadata. Keep it opt-in on shared APIs and let UI adapters decide what to surface.

## Development notes

- Build and lint commands are defined in `composer.json`; prefer those scripts.
- Language files are generated by the maintenance workflow. Run `composer i18n` locally only when checking the generated output before a commit.
